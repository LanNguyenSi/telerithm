## The invariant

`backend/src/api/rest/router.ts` is one 1824-line file: every route, and all authn/authz, live inline - there is no middleware directory. Three caller models are recognised purely from the request shape:

- **Session Bearer.** `resolveUserId` (router.ts:984-992) reads `Authorization: Bearer <token>`, looks it up in `prisma.session`, and throws if missing or expired. `requireAuth` (router.ts:1028-1035) wraps it: returns the userId, or sends 401 and returns `null` so the handler can early-return. (`resolveStreamUserId`/`requireStreamAuth`, router.ts:999-1021, is a header-or-`?token=` variant used only by the SSE `/stream/logs` route, because `EventSource` cannot set headers; the URL token is redacted from the access log by the http logger in `app.ts`.)
- **X-API-Key.** `authenticateApiKey` (router.ts:210-233) reads `X-API-Key`, resolves `prisma.logSource.findUnique({ where: { apiKey } })`, and 403s if the resolved source's `id` does not match the URL's `:sourceId` — the middleware's own comment names this explicitly: "any valid key could forge logs into another source / team (cross-tenant log forgery)". This is the API key's whole tenant boundary: it pins the caller 1:1 to exactly one `LogSource`, with no team/session concept at all. It gates both `POST /ingest/:sourceId` and `POST /ingest/:sourceId/raw` (router.ts:384-421).
- **Global admin.** `requireAdmin` (router.ts:1582-1595) resolves the userId then checks `prisma.user.findUnique(...).role === "ADMIN"` - a Postgres `UserRole`, unrelated to team membership. Gates every `/admin/*` route.

For team-scoped by-id write routes (state-changing, with a `:id`-shaped path param) the convention is: resolve the target resource's owning team, then call `requireTeamRole`, before mutating - not just "the caller is authenticated". `requireResourceTeam(loadTeamId, notFoundMessage, mode)` (router.ts:1129-1147) is the shared factory: given a `loadTeamId(id): Promise<string | null>` resolver, it does load → 404 if the resource doesn't exist → the membership gate chosen by `mode` (403 if not a member, and in `"write"` mode also 403 for a read-only role) → return the teamId. `mode` is a required argument, `"read"` or `"write"`. Five instantiations exist: the write resolvers `requireRuleWriteTeam`, `requireMaintenanceWindowWriteTeam`, `requireIncidentWriteTeam`, `requireIssueWriteTeam`, and the read resolver `requireIncidentTeam` that serves `GET /alerts/incidents/:id/timeline` (router.ts:830, 939, 1203, 1444, 1202).

The factory alone does not stop a future route from skipping the check - nothing forces a handler to call it (router.ts's own comment at the factory site says exactly this). The actual, structural enforcement is `backend/tests/unit/router-team-scoping.test.ts`: it parses `router.ts` via the TypeScript compiler API (it never *imports* router.ts - importing would construct live Prisma/ClickHouse/Redis-backed services as a module-load side effect), extracts every `apiRouter.<method>("path", ...)` call, filters to state-changing (POST/PUT/PATCH/DELETE) routes with a `:param`, and requires each to appear in `ROUTE_TEAM_GUARDS` as either `{ kind: "resolver", resolverName }` (the route must contain a real AST `CallExpression` to that resolver - a mention in a comment does not count, pinned by regression tests) or a justified `{ kind: "allowlist", reason, verify? }`. Two things make this genuinely structural rather than a written convention: a route present in `router.ts` but absent from `ROUTE_TEAM_GUARDS` fails CI immediately, and an `apiRouter.*` registration shape the walker doesn't recognise (`.route()` chaining, `.use()` sub-router mounts, a non-string-literal path) also fails CI instead of silently escaping classification. Shipped as commit `1534e38` (PR #105); documented in German in `ENGINEERING.md:9-45`; this doc is the authoritative English write-up of the same convention.

## Where it's enforced

- **The precedent.** Four cross-tenant IDORs of this exact shape were found and fixed on 2026-07-12: PR #97 (invites), PR #98 (incident actions/timeline), PR #100 (alert-rule mute/unmute), PR #101 (maintenance-window delete). Three of the four had each hand-rolled a near-identical "load by id, check team" helper before PR #105 consolidated them into `requireResourceTeam`; PR #97 (invites) used inline per-route checks instead and still does (see below). A same-day companion fix, PR #102, closed the analogous *read*-path gap on `GET /query/jobs/:id` (router.ts:604-626: "requireAuth alone let any authenticated user read another team's query results (IDOR)") — a read path has no `:id`-write-route shape, so it sits outside this guard's coverage and is tracked separately (agent-tasks `9d86d755`).
- **Allowlist categories, with their justification.** `POST/PUT/PATCH/DELETE /ingest/:sourceId(/raw)` — no team/session exists at all; `authenticateApiKey` itself is the tenant boundary (verified via an `identifier` check that the middleware is actually wired, not a call). `PUT/POST/DELETE /logs/views/:id` and `/subscriptions/:id` — scoped per-(id, teamId) or per-(id, userId) at the Prisma-query level inside the service, so a foreign id paired with the caller's own scope matches nothing rather than needing a pre-check. `POST /teams/:id/invites` — the `:id` path param IS the team itself, not a separate resource to resolve; `requireTeamRole` runs directly against it, further narrowed by `canManageInvites` (below). `POST /invites/:token/accept` — authorization is the unforgeable, single-use, expiring invite token itself, a capability-token pattern, not a membership check (the accepting user isn't a member yet). `DELETE /invites/:id` — loads the invite inline and derives its team (the same resource-derived shape `requireResourceTeam` models), kept inline rather than forced onto the shared factory because it also needs `canManageInvites` on top of plain membership. `/admin/*` — `requireAdmin`'s global role gate supersedes team scoping by design.
- **Invite management needs more than membership.** `canManageInvites(role)` (router.ts:1490-1492) returns `role === "OWNER" || role === "ADMIN"`, gating `POST/GET /teams/:id/invites` and `DELETE /invites/:id` on top of `requireTeamRole`: an invite can grant membership up to role ADMIN and the list payload carries the join token, so mere membership must not be enough (the router's own comment names this as cross-tenant IDOR / privilege escalation prevention).

## The team write rule: VIEWER is read-only

`requireTeamRole` (router.ts:1054-1065, via `resolveTeamRole`, router.ts:1037-1048) checks **membership only**: it looks up `prisma.teamMember.findUnique` and returns whatever `TeamRole` (`OWNER | ADMIN | MEMBER | VIEWER`, `schema.prisma`) the row carries, without asserting a minimum. It stays the gate for read paths. Mutating team-scoped routes use a second gate that also asks the role (operator decision 2026-10-01: VIEWER read-only, MEMBER/ADMIN/OWNER write; implemented under agent-tasks `2a52b2b1`).

The rule has exactly one home, `canWrite(role)` (router.ts:1077-1079), an allow list: OWNER, ADMIN and MEMBER return true, everything else (VIEWER, and any role added later) returns false. `requireTeamWriteRole(userId, teamId, res)` (router.ts:1085-1097) calls `requireTeamRole` (403 for a non-member) and then `canWrite` (403 `{ error: "Forbidden" }` for a read-only role), returning the role or `null` after sending the response, so a handler early-returns before any mutation. Two shapes reach it: routes that take `teamId` from the request body call `requireTeamWriteRole` directly (`POST /sources`, `POST /maintenance-windows`), and by-id routes call a write-mode `requireResourceTeam` resolver (rule mute/unmute, `DELETE /maintenance-windows/:id`, incident acknowledge/resolve/reopen, `PUT /issues/:id`). The read resolver `requireIncidentTeam` keeps the incident timeline readable for a VIEWER.

Enforcement mirrors the by-id guard. `backend/tests/unit/router-write-role.test.ts` parses `router.ts` through the TypeScript AST like `router-team-scoping.test.ts`, but classifies EVERY state-changing `apiRouter` route, with or without a `:param`, because the body-`teamId` routes have no path param. Each must be `{ kind: "write", gate }` (the handler contains a real `CallExpression` to that gate; a comment-only mention does not count) or a justified allowlist entry: public auth, `POST /teams`, API-key ingest, the reading POSTs (`/logs/search`, `/logs/context`, `/logs/facets`, `/logs/histogram`, `/logs/patterns`, `/query/natural`), saved views (owner plus `canManageShared`), per-user subscriptions, invites (`canManageInvites`) and the admin routes (`requireAdmin`). An unclassified new mutating route fails CI. The test also asserts that `requireTeamWriteRole` calls `canWrite`, that `requireResourceTeam` picks `requireTeamWriteRole` in `"write"` mode, and that each write resolver is instantiated with `"write"`. Behaviour (VIEWER 403 with no mutation, MEMBER success, VIEWER timeline 200) is pinned by route tests in `backend/tests/integration/api.test.ts`.

Not decided by this rule: whether a VIEWER may create a shared saved view through `POST /logs/views` (it only checks membership and is allowlisted as the saved-view model; a separate follow-up task owns that question). Invite management (`canManageInvites`), shared-view mutation (`canManageShared`, log-view-service.ts:160-162) and the admin routes keep their own stricter models. After the rule shipped, existing VIEWER memberships lose the write access they had; checking production for them is an operator step recorded on the task.
