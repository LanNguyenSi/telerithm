## The invariant

`backend/src/api/rest/router.ts` is one 1850-line file: every route, and all authn/authz, live inline - there is no middleware directory. Three caller models are recognised purely from the request shape:

- **Session Bearer.** `resolveUserId` (router.ts:998-1006) reads `Authorization: Bearer <token>`, looks it up in `prisma.session`, and throws if missing or expired. `requireAuth` (router.ts:1042-1049) wraps it: returns the userId, or sends 401 and returns `null` so the handler can early-return. (`resolveStreamUserId`/`requireStreamAuth`, router.ts:1013-1035, is a header-or-`?token=` variant used only by the SSE `/stream/logs` route, because `EventSource` cannot set headers; the URL token is redacted from the access log by the http logger in `app.ts`.)
- **X-API-Key.** `authenticateApiKey` (router.ts:210-233) reads `X-API-Key`, resolves `prisma.logSource.findUnique({ where: { apiKey } })`, and 403s if the resolved source's `id` does not match the URL's `:sourceId` — the middleware's own comment names this explicitly: "any valid key could forge logs into another source / team (cross-tenant log forgery)". This is the API key's whole tenant boundary: it pins the caller 1:1 to exactly one `LogSource`, with no team/session concept at all. It gates both `POST /ingest/:sourceId` and `POST /ingest/:sourceId/raw` (router.ts:384-421).
- **Global admin.** `requireAdmin` (router.ts:1608-1621) resolves the userId then checks `prisma.user.findUnique(...).role === "ADMIN"` - a Postgres `UserRole`, unrelated to team membership. Gates every `/admin/*` route.

For team-scoped by-id write routes (state-changing, with a `:id`-shaped path param) the convention is: resolve the target resource's owning team, then call `requireTeamRole`, before mutating - not just "the caller is authenticated". `requireResourceTeam(loadTeamId, notFoundMessage, mode)` (router.ts:1143-1162) is the shared factory: given a `loadTeamId(id): Promise<string | null>` resolver, it does load → 404 if the resource doesn't exist → the membership gate chosen by `mode` (403 if not a member, and in `"write"` mode also 403 for a read-only role) → return the teamId. `mode` is a required argument, `"read"` or `"write"`. Five instantiations exist: the write resolvers `requireRuleWriteTeam`, `requireMaintenanceWindowWriteTeam`, `requireIncidentWriteTeam`, `requireIssueWriteTeam`, and the read resolver `requireIncidentTeam` that serves `GET /alerts/incidents/:id/timeline` (router.ts:844, 953, 1218, 1459, 1217).

The factory alone does not stop a future route from skipping the check - nothing forces a handler to call it (router.ts's own comment at the factory site says exactly this). The actual, structural enforcement is `backend/tests/unit/router-team-scoping.test.ts`: it parses `router.ts` via the TypeScript compiler API (it never *imports* router.ts - importing would construct live Prisma/ClickHouse/Redis-backed services as a module-load side effect), extracts every `apiRouter.<method>("path", ...)` call, filters to state-changing (POST/PUT/PATCH/DELETE) routes with a `:param`, and requires each to appear in `ROUTE_TEAM_GUARDS` as either `{ kind: "resolver", resolverName }` (the route must contain a real AST `CallExpression` to that resolver - a mention in a comment does not count, pinned by regression tests) or a justified `{ kind: "allowlist", reason, verify? }`. Two things make this genuinely structural rather than a written convention: a route present in `router.ts` but absent from `ROUTE_TEAM_GUARDS` fails CI immediately, and an `apiRouter.*` registration shape the walker doesn't recognise (`.route()` chaining, `.use()` sub-router mounts, a non-string-literal path) also fails CI instead of silently escaping classification. Shipped as commit `1534e38` (PR #105); documented in German in `ENGINEERING.md:9-45`; this doc is the authoritative English write-up of the same convention.

## Where it's enforced

- **The precedent.** Four cross-tenant IDORs of this exact shape were found and fixed on 2026-07-12: PR #97 (invites), PR #98 (incident actions/timeline), PR #100 (alert-rule mute/unmute), PR #101 (maintenance-window delete). Three of the four had each hand-rolled a near-identical "load by id, check team" helper before PR #105 consolidated them into `requireResourceTeam`; PR #97 (invites) used inline per-route checks instead and still does (see below). A same-day companion fix, PR #102, closed the analogous *read*-path gap on `GET /query/jobs/:id` (router.ts:604-626: "requireAuth alone let any authenticated user read another team's query results (IDOR)") — a read path has no `:id`-write-route shape, so it sits outside this guard's coverage and is tracked separately (agent-tasks `9d86d755`).
- **Allowlist categories, with their justification.** `POST/PUT/PATCH/DELETE /ingest/:sourceId(/raw)` - no team/session exists at all; `authenticateApiKey` itself is the tenant boundary (verified via an `identifier` check that the middleware is actually wired, not a call). `PUT/POST/DELETE /logs/views/:id` and `/subscriptions/:id` - scoped per-(id, teamId) or per-(id, userId) inside the service (views: load, team match, then owner-or-`canManageShared`; subscriptions: the Prisma query itself), so a foreign id paired with the caller's own scope matches nothing rather than needing a pre-check. This is cross-tenant scoping only; the shared-state gate on create and update is described under the team write rule below. `POST /teams/:id/invites` - the `:id` path param IS the team itself, not a separate resource to resolve; `requireTeamRole` runs directly against it, further narrowed by `canManageInvites` (below). `POST /invites/:token/accept` - authorization is the unforgeable, single-use, expiring invite token itself, a capability-token pattern, not a membership check (the accepting user isn't a member yet). `DELETE /invites/:id` - loads the invite inline and derives its team (the same resource-derived shape `requireResourceTeam` models), kept inline rather than forced onto the shared factory because it also needs `canManageInvites` on top of plain membership. `/admin/*` - `requireAdmin`'s global role gate supersedes team scoping by design.
- **Invite management needs more than membership.** `canManageInvites(role)` (router.ts:1505-1507) returns `role === "OWNER" || role === "ADMIN"`, gating `POST/GET /teams/:id/invites` and `DELETE /invites/:id` on top of `requireTeamRole`: an invite can grant membership up to role ADMIN and the list payload carries the join token, so mere membership must not be enough (the router's own comment names this as cross-tenant IDOR / privilege escalation prevention).

## The team write rule: VIEWER is read-only

`requireTeamRole` (router.ts:1068-1079, via `resolveTeamRole`, router.ts:1051-1062) checks **membership only**: it looks up `prisma.teamMember.findUnique` and returns whatever `TeamRole` (`OWNER | ADMIN | MEMBER | VIEWER`, `schema.prisma`) the row carries, without asserting a minimum. It stays the gate for read paths. Mutating team-scoped routes use a second gate that also asks the role (operator decision 2026-10-01: VIEWER read-only, MEMBER/ADMIN/OWNER write; implemented under agent-tasks `2a52b2b1`).

The rule has exactly one home, `canWrite(role)` (router.ts:1091-1093), an allow list: OWNER, ADMIN and MEMBER return true, everything else (VIEWER, and any role added later) returns false. `requireTeamWriteRole(userId, teamId, res)` (router.ts:1099-1111) calls `requireTeamRole` (403 for a non-member) and then `canWrite` (403 `{ error: "Forbidden" }` for a read-only role), returning the role or `null` after sending the response, so a handler early-returns before any mutation. Two shapes reach it: routes that take `teamId` from the request body call `requireTeamWriteRole` directly (`POST /sources`, `POST /maintenance-windows`), and by-id routes call a write-mode `requireResourceTeam` resolver (rule mute/unmute, `DELETE /maintenance-windows/:id`, incident acknowledge/resolve/reopen, `PUT /issues/:id`). The read resolver `requireIncidentTeam` keeps the incident timeline readable for a VIEWER.

Enforcement mirrors the by-id guard. `backend/tests/unit/router-write-role.test.ts` parses `router.ts` through the TypeScript AST like `router-team-scoping.test.ts`, but classifies EVERY state-changing `apiRouter` route, with or without a `:param`, because the body-`teamId` routes have no path param. Each must be `{ kind: "write", gate }` or a justified allowlist entry. For a write entry the gate must be a top-level statement of the handler body, preceded only by whitelisted auth and validation statements (`requireAuth`, `safeParse` with its early return) and its `null` result must end the handler, either as `if ((await gate(...)) === null) return;` or as `const x = await gate(...)` immediately followed by `if (x === null) return;`; a gate called after a mutation or another await, with its result unchecked, with a non-returning check, nested in a condition or callback, or mentioned only in a comment fails. The check is syntactic: it does not see side effects inside the gate call's arguments, in middleware arguments before the handler, in handler default parameters, or in tagged templates and `new` expressions; `router.ts` uses none of those shapes today. The allowlist entries are: public auth, `POST /teams`, API-key ingest, the reading POSTs (`/logs/search`, `/logs/context`, `/logs/facets`, `/logs/histogram`, `/logs/patterns`, `/query/natural`), saved views (owner plus `canManageShared`, with the caveat below), per-user subscriptions, invites (`canManageInvites`) and the admin routes (`requireAdmin`). An unclassified new mutating route fails CI, and so does an `apiRouter` registration the walker cannot classify: any reference to `apiRouter` other than its declaration and a direct `apiRouter.<method>(` call (an alias, `apiRouter["delete"](...)`, a detached method, destructuring) is flagged, and `router-team-scoping.test.ts` carries the same check. The test also asserts that `requireTeamWriteRole` calls `canWrite`, that `requireResourceTeam` fails closed (only an explicit `"read"` mode takes `requireTeamRole`, everything else takes `requireTeamWriteRole`), and that each write resolver is instantiated with `"write"`. Behaviour (VIEWER 403 with no mutation, MEMBER success, VIEWER timeline 200) is pinned by route tests in `backend/tests/integration/api.test.ts`.

Not covered by this rule, and not read-only for a VIEWER: the saved-view routes (`/logs/views`). A private view is per-user state, so any member, VIEWER included, may create it and edit its own. Team-wide state has its own gate: `canManageShared(role)` (router.ts:1516-1518, next to `canManageInvites`) is true for OWNER and ADMIN only, and `POST /logs/views` and `PUT /logs/views/:id` answer 403 before any service call when the payload sets `isShared: true` or `isDefault: true` and the role fails it (`requestsSharedState`, router.ts:629-631). `isDefault: true` counts as team-wide because `create` and `update` run an `updateMany` (log-view-service.ts:55 and 95) that clears the default flag of the caller's own views and of every shared view in the team, foreign ones included; gating before the service means that `updateMany` never runs for a MEMBER or VIEWER. The service-level update, delete and duplicate paths receive the same predicate as `canManageShared`: `canMutate` (log-view-service.ts:160-162) lets the owner or, for a shared view, OWNER/ADMIN act, and `POST /logs/views/:id/duplicate` checks `canRead` and keeps `isShared` only when `canManageShared` is true (log-view-service.ts:121 and 129). The allowlist entries for these routes in the write-role meta-test record this split (agent-tasks `765bb823`). Remaining gap: the gate fires only when the payload sets `isShared: true` or `isDefault: true`, so a non-admin who owns a view that is already shared or default (created before the gate shipped, or after an admin was demoted) can still edit it, unshare it and delete it, because `canMutate` lets the owner act. Existing data is not migrated; counting such views in production is an operator step recorded on the task. For MEMBER and VIEWER, `isDefault: true` is refused even on a private view, since the service clears the team's default flags. Invite management (`canManageInvites`) and the admin routes keep their own stricter models. After the rule shipped, existing VIEWER memberships lose the write access they had; checking production for them is an operator step recorded on the task.
