## The invariant

`backend/src/api/rest/router.ts` is one 1767-line file: every route, and all authn/authz, live inline - there is no middleware directory. Three caller models are recognised purely from the request shape:

- **Session Bearer.** `resolveUserId` (router.ts:962-970) reads `Authorization: Bearer <token>`, looks it up in `prisma.session`, and throws if missing or expired. `requireAuth` (router.ts:1006-1013) wraps it: returns the userId, or sends 401 and returns `null` so the handler can early-return. (`resolveStreamUserId`/`requireStreamAuth`, router.ts:977-999, is a header-or-`?token=` variant used only by the SSE `/stream/logs` route, because `EventSource` cannot set headers; the URL token is redacted from the access log by the http logger in `app.ts`.)
- **X-API-Key.** `authenticateApiKey` (router.ts:216-241) reads `X-API-Key`, resolves `prisma.logSource.findUnique({ where: { apiKey } })`, and 403s if the resolved source's `id` does not match the URL's `:sourceId` - the middleware's own comment names this explicitly: "any valid key could forge logs into another source / team (cross-tenant log forgery)". This is the API key's whole tenant boundary: it pins the caller 1:1 to exactly one `LogSource`, with no team/session concept at all. It gates both `POST /ingest/:sourceId` and `POST /ingest/:sourceId/raw` (router.ts:379-419).
- **Global admin.** `requireAdmin` (router.ts:1525-1538) resolves the userId then checks `prisma.user.findUnique(...).role === "ADMIN"` - a Postgres `UserRole`, unrelated to team membership. Gates every `/admin/*` route.

For a team-scoped mutating route the convention is: authenticate, resolve the team the request acts on (from the body, or from the target resource), and apply the team write gate, all before the handler touches anything - not just "the caller is authenticated". That order is no longer a convention a handler has to remember; it is the body of one wrapper. `writeRoute(method, path, resolveTeam, handler)` (`createWriteRoute` in `backend/src/api/rest/write-route.ts`, bound once in router.ts:75 to `apiRouter`, `requireAuth` and `requireTeamWriteRole`) runs, in this order: `requireAuth` (401), `resolveTeam` (400 for an invalid body, 404 for an unknown resource), `requireTeamWriteRole` (403 for a non-member or a read-only role), and only then the handler, which receives `{ req, res, userId, teamId, role, input }`. The handler is invoked from exactly one place in the wrapper, after the gate. `resolveTeam` is built by one of two factories: `teamFromBody(schema)` validates the body and takes `teamId` from it (`POST /sources`, `POST /maintenance-windows`), `teamFromResource(loadTeamId, notFoundMessage, bodySchema?)` loads the resource named by `:id` and takes its owning team, optionally validating the body first (rule mute with `muteRuleSchema`, `PUT /issues/:id` with `issueUpdateSchema`; unmute, maintenance-window delete and incident acknowledge/resolve/reopen pass no schema). The nine team-scoped write routes are all registered this way, with the same status codes and mutations as before.

The remaining read-side factory is `requireResourceTeam(loadTeamId, notFoundMessage)` (router.ts:1093-1107): load, 404 if missing, `requireTeamRole` (membership only), return the teamId. It has no mode argument any more; its only user is `GET /alerts/incidents/:id/timeline`, which a VIEWER may read. It is not a write gate, and a mutating route cannot use it to avoid the write rule because the meta-test below fails any mutating route that is not `writeRoute`-registered or allowlisted.

The by-id team-resolution half is enforced by `backend/tests/unit/router-team-scoping.test.ts`: it parses `router.ts` via the TypeScript compiler API (it never *imports* router.ts - importing would construct live Prisma/ClickHouse/Redis-backed services as a module-load side effect), extracts every `apiRouter.<method>("path", ...)` and `writeRoute("<method>", "path", ...)` registration, filters to state-changing (POST/PUT/PATCH/DELETE) routes with a `:param`, and requires each to appear in `ROUTE_TEAM_GUARDS` as either `{ kind: "resolver", loaderName }` (the route must be `writeRoute`-registered with a `teamFromResource(<loaderName>, ...)` resolver, inline or in a top-level const - a mention in a comment does not count, pinned by regression tests) or a justified `{ kind: "allowlist", reason, verify? }`. A route present in `router.ts` but absent from `ROUTE_TEAM_GUARDS` fails CI immediately, and an `apiRouter.*` registration shape the walker doesn't recognise (`.route()` chaining, `.use()` sub-router mounts, a non-string-literal path, an alias) also fails CI instead of silently escaping classification. Originally shipped as commit `1534e38` (PR #105); documented in German in `ENGINEERING.md`; this doc is the authoritative English write-up of the same convention.

## Where it's enforced

- **The precedent.** Four cross-tenant IDORs of this exact shape were found and fixed on 2026-07-12: PR #97 (invites), PR #98 (incident actions/timeline), PR #100 (alert-rule mute/unmute), PR #101 (maintenance-window delete). Three of the four had each hand-rolled a near-identical "load by id, check team" helper before PR #105 consolidated them into `requireResourceTeam`; PR #97 (invites) used inline per-route checks instead and still does (see below). A same-day companion fix, PR #102, closed the analogous *read*-path gap on `GET /query/jobs/:id` (router.ts:600-621: "requireAuth alone let any authenticated user read another team's query results (IDOR)") - a read path has no `:id`-write-route shape, so it sits outside this guard's coverage and is tracked separately (agent-tasks `9d86d755`).
- **Allowlist categories, with their justification.** `POST/PUT/PATCH/DELETE /ingest/:sourceId(/raw)` - no team/session exists at all; `authenticateApiKey` itself is the tenant boundary (verified via an `identifier` check that the middleware is actually wired, not a call). `PUT/POST/DELETE /logs/views/:id` and `/subscriptions/:id` - scoped per-(id, teamId) or per-(id, userId) inside the service (views: load, team match, then owner-or-`canManageShared`; subscriptions: the Prisma query itself), so a foreign id paired with the caller's own scope matches nothing rather than needing a pre-check. This is cross-tenant scoping only; the shared-state gate on create and update is described under the team write rule below. `POST /teams/:id/invites` - the `:id` path param IS the team itself, not a separate resource to resolve; `requireTeamRole` runs directly against it, further narrowed by `canManageInvites` (below). `POST /invites/:token/accept` - authorization is the unforgeable, single-use, expiring invite token itself, a capability-token pattern, not a membership check (the accepting user isn't a member yet). `DELETE /invites/:id` - loads the invite inline and derives its team (the same resource-derived shape `teamFromResource` models), kept inline rather than forced onto the shared wrapper because it also needs `canManageInvites` on top of plain membership. `/admin/*` - `requireAdmin`'s global role gate supersedes team scoping by design.
- **Invite management needs more than membership.** `canManageInvites(role)` (router.ts:1422-1424) returns `role === "OWNER" || role === "ADMIN"`, gating `POST/GET /teams/:id/invites` and `DELETE /invites/:id` on top of `requireTeamRole`: an invite can grant membership up to role ADMIN and the list payload carries the join token, so mere membership must not be enough (the router's own comment names this as cross-tenant IDOR / privilege escalation prevention).

## The team write rule: VIEWER is read-only

`requireTeamRole` (router.ts:1032-1043, via `resolveTeamRole`, router.ts:1015-1026) checks **membership only**: it looks up `prisma.teamMember.findUnique` and returns whatever `TeamRole` (`OWNER | ADMIN | MEMBER | VIEWER`, `schema.prisma`) the row carries, without asserting a minimum. It stays the gate for read paths. Mutating team-scoped routes use a second gate that also asks the role (operator decision 2026-10-01: VIEWER read-only, MEMBER/ADMIN/OWNER write; implemented under agent-tasks `2a52b2b1`).

The rule has exactly one home, `canWrite(role)` (router.ts:1054-1056), an allow list: OWNER, ADMIN and MEMBER return true, everything else (VIEWER, and any role added later) returns false. `requireTeamWriteRole(userId, teamId, res)` (router.ts:1062-1074) calls `requireTeamRole` (403 for a non-member) and then `canWrite` (403 `{ error: "Forbidden" }` for a read-only role), returning the role or `null` after sending the response. The only caller of the write gate on a route's behalf is `writeRoute`, so the gate cannot be skipped, reordered or given arguments by a route author: the signature has no middleware argument, the gate call sits in the wrapper with fixed arguments (the authenticated user and the team the resolver returned), and the handler, with its default parameters, tagged templates and `new` expressions, is called by the wrapper after the gate. Two route-supplied inputs do run before the gate, because the gate needs the team they produce: the loader given to `teamFromResource` and the body schema given to `teamFromBody`/`teamFromResource`, including any transform, refinement or preprocess step it carries. Both must be free of side effects; the wrapper cannot sandbox them and the tests only force them to be named, reviewable code (see the limits below). The read resolver keeps the incident timeline readable for a VIEWER.

Enforcement makes the wrapper mandatory instead of recognising gate placements, in two layers. The authoritative one is `backend/tests/unit/route-table.test.ts`: it builds the real app with `createApp()` (the module mocks of `backend/tests/integration/api.test.ts`), walks the Express 4 layer stack (`app._router.stack`) recursively, mounted routers included, and requires that (1) every layer of the app and of the API router is on a known list (name, mount path and arity, plus a source fragment for the anonymous request-logging and error-handler layers), so an extra router, an inline `app.use(...)` or router-level middleware fails; (2) no state-changing route (anything but GET/HEAD/OPTIONS, `app.all` included) exists outside the one `apiRouter` mounted at `/api/v1`; (3) every state-changing route of the API router is classified in `ROUTE_WRITE_GUARDS` (`backend/tests/unit/route-guards.ts`), is registered once, and no classification is stale; (4) a `{ kind: "write" }` route is served by exactly one handler, the one `writeRoute` registered (`write-route.ts` records it in a `WeakSet`, read through `isWriteRouteHandler`), and an allowlisted route is not served by the wrapper and carries a justification. Because it reads the registered stack instead of the source text, it does not depend on how a route was spelled: an aliased `Router`, a path held in a const, a second router mounted in `app.ts` and an inline mutating `app.use` are all reported, and the file carries a synthetic control for each. The second layer is `backend/tests/unit/router-write-role.test.ts`, which parses `router.ts` through the TypeScript AST (walker shared with `router-team-scoping.test.ts` in `backend/tests/unit/router-ast.ts`) and keeps what the runtime table cannot see. It classifies the routes by their registration (a "write" entry registered with `apiRouter`, an allowlist entry registered with `writeRoute`, a route in neither list and a stale entry all fail). Every `writeRoute` call must be a top-level statement of the shape `(method, path, resolver, handler)` with a literal post/put/patch/delete method and path, a resolver that is a `teamFromBody(...)`/`teamFromResource(...)` call (inline or held in a top-level const) and a function as handler, and no other reference to the identifier `writeRoute`. The factory arguments are plain identifiers: the body schema is imported, without renaming, from `validation/schemas`, the loader is a top-level const arrow function, and the not-found message is a string literal, so no inline `transform`, `refine` or `safeParse` object can sit in a pre-gate slot. `router.ts` may not declare or alias `teamFromBody`, `teamFromResource`, `writeRoute` or `createWriteRoute` (a nested look-alike would pass the shape checks), and the binding `const writeRoute = createWriteRoute({ router: apiRouter, requireAuth, requireTeamWriteRole })` must exist once with exactly those three properties (swapping in the membership-only `requireTeamRole` would type-check, so the test pins it). A direct AST check pins that `write-route.ts` calls the handler once, after the `requireTeamWriteRole` call, and `write-route.test.ts` proves the behaviour: auth, then resolver, then gate, then handler, with a denied caller never reaching the handler or its parameter defaults, tagged templates and `new` expressions. The allowlist entries are: public auth, `POST /teams`, API-key ingest, the reading POSTs (`/logs/search`, `/logs/context`, `/logs/facets`, `/logs/histogram`, `/logs/patterns`, `/query/natural`), saved views (owner plus `canManageShared`, with the caveat below), per-user subscriptions, invites (`canManageInvites`) and the admin routes (`requireAdmin`). The test also asserts that `requireTeamWriteRole` calls `canWrite`, and that `requireResourceTeam` calls only the membership gate. Behaviour (VIEWER 403 with no mutation, MEMBER success, VIEWER timeline 200) is pinned by route tests in `backend/tests/integration/api.test.ts`.

How the shapes the earlier placement check could not see are answered now. A side effect in the arguments of the gate call (S0) cannot be written, since the route never calls the gate. A mutating middleware argument before the handler (S1) is rejected by the `writeRoute` shape check (a fifth argument or spread), and on `apiRouter.<method>` it is an unclassified mutating route. A default-parameter initializer on the handler (S2) and a tagged template or `new` expression in the handler (S3) run only inside the handler, which the wrapper calls after the gate; synthetic handlers in `write-route.test.ts` show they do not execute for a denied caller. The same shapes on an `apiRouter.<method>` registration fail the classification instead. A second `Router()` instance, `apiRouter` used from another module, a router mounted in `app.ts` or a mutating `app.use` (S4) is detected at runtime by the route table whatever its spelling. The static scan of every file in `backend/src` stays for code outside `createApp()` that the table does not walk, such as a registration on the app in `server.ts` or a second express app in the same process: `Router()` may be called once (router.ts), `express()` only in app.ts and config/index.ts, `createWriteRoute` once (router.ts), nothing outside router.ts may register a route with a path or mount a router (app.ts mounts only `/docs` and `/api/v1`), and `apiRouter` may be referenced outside router.ts only as app.ts's import and its `/api/v1` mount. Residual limits: the bodies of the named loaders and of the schemas in `validation/schemas.ts` (a `transform` defined there) run before the gate and are trusted to be free of side effects - a review item, since neither test inspects them; the application-level known list is exact, so adding a middleware to `createApp()` means updating `route-table.test.ts` on purpose; mutating `GET` routes are not classified, because the routes are keyed by method.

Not covered by this rule, and not read-only for a VIEWER: the saved-view routes (`/logs/views`). A private view is per-user state, so any member, VIEWER included, may create it and edit its own. Team-wide state has its own gate: `canManageShared(role)` (router.ts:1433-1435, next to `canManageInvites`) is true for OWNER and ADMIN only, and `POST /logs/views` and `PUT /logs/views/:id` answer 403 before any service call when the payload sets `isShared: true` or `isDefault: true` and the role fails it (`requestsSharedState`, router.ts:624-626). `isDefault: true` counts as team-wide because `create` and `update` run an `updateMany` (log-view-service.ts:55 and 95) that clears the default flag of the caller's own views and of every shared view in the team, foreign ones included; gating before the service means that `updateMany` never runs for a MEMBER or VIEWER. The service-level update, delete and duplicate paths receive the same predicate as `canManageShared`: `canMutate` (log-view-service.ts:160-162) lets the owner or, for a shared view, OWNER/ADMIN act, and `POST /logs/views/:id/duplicate` checks `canRead` and keeps `isShared` only when `canManageShared` is true (log-view-service.ts:121 and 129). The allowlist entries for these routes in the write-role meta-test record this split (agent-tasks `765bb823`). Remaining gap: the gate fires only when the payload sets `isShared: true` or `isDefault: true`, so a non-admin who owns a view that is already shared or default (created before the gate shipped, or after an admin was demoted) can still edit it, unshare it and delete it, because `canMutate` lets the owner act. Existing data is not migrated; counting such views in production is an operator step recorded on the task. For MEMBER and VIEWER, `isDefault: true` is refused even on a private view, since the service clears the team's default flags. Invite management (`canManageInvites`) and the admin routes keep their own stricter models. After the rule shipped, existing VIEWER memberships lose the write access they had; checking production for them is an operator step recorded on the task.
