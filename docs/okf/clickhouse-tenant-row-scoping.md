## The invariant

The four aggregation/search methods share `LogRepository.buildScopedWhere` (`backend/src/repositories/log-repository.ts:458#"private buildScopedWhere("`), which builds the `WHERE` clause as parameterised ClickHouse SQL. The **first** condition it pushes, unconditionally, is `team_id = {teamId:String}` (`log-repository.ts:467#"const conditions: string[] = ["`) — every other condition (`source_id`, `timestamp` range, ad-hoc filters, free-text search) is appended after it. The four query methods route through it: `search` (`log-repository.ts:79-81#"const { where, params } = this.buildScopedWhere(query);"`), `getFacets` (`log-repository.ts:145-154#"const { where, params } = this.buildScopedWhere(query);"`), `getHistogram` (`log-repository.ts:177-178#"const { where, params } = this.buildScopedWhere(query);"`), and `getPatterns` (`log-repository.ts:203-204#"const { where, params } = this.buildScopedWhere(query);"`) each call `this.buildScopedWhere(query)` before composing their own aggregation SQL around the resulting `where`/`params`. This is a second, independent tenancy layer *below* `router.ts`'s session/team authz (see [api-authz-and-team-scoping.md](api-authz-and-team-scoping.md)): even if a route-level check were ever missed, none of these methods can execute without a `team_id` predicate, because `teamId` is a required field of every query shape `buildScopedWhere` accepts and it is always conditions[0]. Three further public methods read the `logs` table WITHOUT `buildScopedWhere` and instead place the same `team_id = {teamId:String}` predicate first by hand: `getStats` (`log-repository.ts:269#"async getStats("`, predicates at `log-repository.ts:278-288#"SELECT service, count() as cnt FROM logs WHERE team_id = {teamId:String}"`), `getContext` (`log-repository.ts:308#"async getContext("`, scope condition at `log-repository.ts:325#"const scopeConditions: string[] ="`), and `findById` (`log-repository.ts:572#"async findById("`, predicate at `log-repository.ts:576#"WHERE team_id = {teamId:String}"`). One more reader of the `logs` table lives outside `LogRepository`: `AlertEvaluationWorker.queryLogCount` (`backend/src/services/alert/alert-evaluation-worker.ts:169#"private async queryLogCount("`) runs its own `clickhouse.query`, the only such call in `backend/src` outside `log-repository.ts`, and also places the predicate first by hand (`backend/src/services/alert/alert-evaluation-worker.ts:175#"FROM logs WHERE team_id = {teamId:String}"`). Its `teamId` is the evaluated rule's own team, and the rule's `query` text is bound as the `{pattern:String}` parameter of a `message ILIKE` condition, not spliced into the SQL. The real invariant is therefore "team_id is the first predicate in every logs read", not "every read goes through buildScopedWhere": an auditor must check every logs read, including the alert worker's count query, not just the shared builder.

The clause is only as safe as the values that can reach it. Non-searchable filter fields go through `fields['<key>']`, ClickHouse's map-indexing syntax over the `logs` table's `Map(String, String)` column (`backend/clickhouse/init.sql`). Building that literal from a caller-controlled `filter.field` string is a WHERE-clause breakout risk if the key isn't sanitised — a crafted key like `x'] OR 1=1 OR fields['x` could otherwise neutralise the parameterised `team_id` scope entirely. `buildFilterCondition` (`log-repository.ts:400#"private buildFilterCondition("`) closes this: any field not in `SEARCHABLE_COLUMNS` (`level`, `service`, `host`, `message`) is lowercased and stripped to `[^a-z0-9_-]` (`log-repository.ts:428#"filter.field.toLowerCase().replace(/[^a-z0-9_-]/g"`, "the same allow-list used for free-text search"); if nothing safe remains the filter is dropped (`return null`) rather than emitted with an empty key.

## Where it's enforced

- **`buildScopedWhere`** (`log-repository.ts:458#"private buildScopedWhere("`): pushes `team_id` first, then conditionally `source_id`, `timestamp >= / <=` (converted via `toChTimestamp`), each `filters[]` entry via `buildFilterCondition`, and — only when `query.queryType === "sql"` — a free-text search condition. All values are bound through ClickHouse's `{name:Type}` parameter syntax, never string-interpolated directly into the clause.
- **The map-key sanitiser** (`log-repository.ts:422-432#"fields['${safeKey}']"`): the *same* regex allow-list (`[^a-z0-9_-]` stripped, lowercased) gates both the dynamic filter-field path and (per its own comment) the free-text search path, so there is one sanitisation rule to keep in sync, not two independently-maintained ones. This closed a real finding: PR #75's CHANGELOG entry documents "ClickHouse SQLi: `log-repository.ts buildFilterCondition` now sanitises the dynamic map key against the existing allow-list regex so a crafted `filter.field` cannot break out of the `fields['<key>']` literal" as one of four HIGH audit findings closed in that release.
- **`queryType: "sql"` is a legacy misnomer, not a raw-SQL surface.** `searchSchema` (`backend/src/validation/schemas.ts:122#"export const searchSchema = z.object({"`) defines `queryType: z.enum(["sql", "natural"]).default("sql")`. Despite the name, the `"sql"` branch never accepts or executes caller-supplied SQL: `buildSearchCondition` (`log-repository.ts:505#"private buildSearchCondition("`) tokenizes the query string on whitespace, sanitises each token to `[a-z0-9_-]` (dropping tokens of length <= 1), expands a small set of stemming variants (`fail`/`failed`/`failure`/`failures`/`failing`), and ANDs together per-token ILIKE conditions over `message`/`service`/`host`, each bound as a parameter. "sql" here means "the structured/manual query mode" as opposed to `"natural"` (the NLQ-translated mode, see [nlq-pipeline.md](nlq-pipeline.md)) — there is no code path where a user-supplied string is concatenated into the query as SQL.

## What breaks it

- A new `LogRepository` query method that composes its own `WHERE` clause without calling `buildScopedWhere` (or that calls it but then discards/reorders the returned string) would read across all teams' rows with no tenant boundary at all — there is no second gate to catch this. The same applies to edits of the three hand-scoped methods (findById/getContext/getStats) and of the alert worker's `queryLogCount`, and to any new `clickhouse.query` call outside `LogRepository`: dropping or omitting the inline `team_id` predicate is equally fatal, and nothing shared would catch it. The tenancy contract is "team_id first in every logs read", enforced per-method.
- A new dynamic-field code path (e.g. a facet or sort field built from a caller string) that does not route through the same `[^a-z0-9_-]` allow-list sanitiser as `buildFilterCondition`/`buildSearchCondition` re-opens the WHERE-breakout class PR #75 closed. Two independently-drifting sanitisers (rather than the one shared regex) is itself a smaller version of the same risk.
- Treating `queryType: "sql"` as license to accept literal SQL from a request body — it is a naming artifact from the tokenized free-text path, not a raw-SQL feature; adding real SQL passthrough here would be a new, unreviewed injection surface.
