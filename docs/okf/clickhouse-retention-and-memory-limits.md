`backend/clickhouse/` ships `init.sql` (schema bootstrap), the directory `backend/clickhouse/config.d/` with `limits.xml` and `system-logs.xml` (both overrides) plus a copy of the image's own `docker_related_config.xml`, and the directory `backend/clickhouse/users.d/` with the `limits.xml` that holds the settings profile. They only take effect if they are actually mounted into the running container. `config.d` is mounted as a whole over the image's `/etc/clickhouse-server/config.d` (not file by file, see the last section), which hides the image's own `config.d` content, hence the copy; `users.d` is mounted the same way over `/etc/clickhouse-server/users.d`, where the image ships no file (checked on 24.10.2.80 and 24.12.6.70), although its entrypoint can write one at start (last section). The mounts are asserted identical between the two prod composes in [compose-file-topology-and-drift.md](compose-file-topology-and-drift.md); this doc covers what each one actually does and the gotchas around it.

## system-logs.xml — disable text_log, TTL the rest

ClickHouse's internal `system.text_log` duplicates the server's stderr into a MergeTree table with no TTL by default. On 2026-07-15 it held 133 GiB / 2.5 billion rows on VPS-01 — roughly 80% of the whole disk — while the actual telerithm application data stayed tiny. `system-logs.xml` (`backend/clickhouse/config.d/system-logs.xml`) responds in two parts: `<text_log remove="1"/>` disables it outright (it is pure ClickHouse-internal diagnostics, not telerithm data), and so does `remove="1"` for `metric_log`, `asynchronous_metric_log`, `trace_log`, `processors_profile_log` and `query_metric_log`, which telerithm never reads; `metric_log` (one wide row per second) had grown to 2.16 GiB in 516 active parts on VPS-01 by 2026-10-24, far beyond 7 days of rows (the cause is unverified: a fresh table does carry the 7-day TTL, so the production table may predate the TTL config), and its background merges kept about two CPU cores busy. The remaining system log tables (`query_log`, `query_thread_log`, `part_log`, `error_log`) get `event_date + INTERVAL 7 DAY DELETE` so short-window debugging stays possible without unbounded growth. A disabled log's existing table stays on disk after the restart but is no longer written; drop it by hand after the restart, because its existing parts can still be merged in the background.

**Caveat, stated in the file's own header comment:** a TTL config change only applies to *newly created* tables. On the first restart after this file is mounted, ClickHouse renames each existing table to `<name>_N` and creates a fresh one carrying the TTL — the renamed leftovers keep whatever data they already had and are not themselves retroactively pruned; they can be dropped by hand if they matter for disk space (after the 2026-07-15 truncate they were empty on VPS-01, but that will not be true on every deploy of this config). Shipped together with bounded container logs (`docker-compose.prod.yml`/`docker-compose.traefik.yml`'s `x-logging` anchor, json-file 10m x 3) as commit `b3744ec` / `7248959` (PR #110): "system.text_log had no TTL and grew to 133 GiB ... while actual telerithm data stayed tiny. Disable text_log outright ... and give every other system log table a 7-day TTL."

## limits.xml — memory ceiling, the per-query profile, and the ratio=0 footgun

Two files, because ClickHouse reads two kinds of settings from two places. `config.d/limits.xml` sets the server setting `max_server_memory_usage_to_ram_ratio: 0.85` (about 2.55 GiB in the 3 GiB container). `users.d/limits.xml` holds the `default` settings profile: `max_memory_usage: 2147483648` (2 GiB per query) and `max_bytes_before_external_group_by`/`max_bytes_before_external_sort: 1073741824` (1 GiB, the thresholds above which `GROUP BY` and `ORDER BY` spill to disk). ClickHouse reads profiles only from the users config (`users.xml` and `users.d`), never from `config.d`: until 2026-10-25 the profile block sat in `config.d/limits.xml` and `system.settings` showed all three settings as 0 in a running container, so only the ratio applied. Measured 2026-10-25 on `clickhouse/clickhouse-server:24` (24.10.2.80) started from `docker-compose.traefik.yml` and from `docker-compose.prod.yml`: with the profile in `config.d` the three settings read 0 and a `groupArray` over 1 billion numbers was stopped by "Memory limit (total) exceeded ... maximum: 2.55 GiB"; with the profile in `users.d` they read 2147483648, 1073741824 and 1073741824 and the same query fails with `MEMORY_LIMIT_EXCEEDED` "Memory limit (for query) exceeded ... maximum: 2.00 GiB". Removing the `users.d` mount line from either compose file brings all three back to 0. The spill engages: a 20-million-key aggregation wrote 3 parts to disk and peaked at 1.00 GiB, where without the profile it peaked at 1.50 GiB. A changed file in `users.d` is applied within seconds to new queries without a restart (a replaced `max_memory_usage` was seen after 5 seconds).

**The caps and the heaviest queries.** The queries in `backend/src/repositories/log-repository.ts` run over at most `maxLookbackMs` (7 days). On 8 million rows over 7 days for one team (and a second table of 4 million rows whose every message is unique), peak query memory with the profile active: patterns aggregation (`GROUP BY` on the signature expression, `any(message)`) 1.01 GiB with the spill engaged (16 parts) and, with every message unique, 1.01 GiB (8 parts), against 1.64 GiB without the profile on the unique data and a failure at the server-wide limit on the 8-million-row table; search with `ORDER BY level` at `LIMIT 500 OFFSET 9500` 946 MiB (957 MiB without the profile); search by timestamp 255 MiB; a facet over a high-cardinality map key 301 MiB; the service facet, the histogram, the stats and the alert-count queries under 10 MiB. None comes near 2 GiB, and the aggregations that were closest to the server limit now finish through the spill. A query that needs more than 2 GiB fails with `MEMORY_LIMIT_EXCEEDED` instead of growing until the server-wide limit. The spill is not a guarantee in a 3 GiB container: a synthetic aggregation over 30 million distinct keys with `max_threads=2` still ended at "Memory limit (total) exceeded" because the server's resident memory reached 2.55 GiB while the query itself was accounted at 1 GiB, so the container limit stays the real ceiling. The cap is per query: it does not bound how many queries run at once, so several queries that each stay under 2 GiB can still add up to the server-wide limit (about 2.55 GiB); that case was not measured.

**Why the server-wide setting is ratio-only rather than an absolute cap.** PR #59 (CHANGELOG.md, `[0.1.1]`) first raised the container to 3 GiB and introduced `limits.xml` after a ClickHouse OOM on the dashboard-overview aggregation (1 GiB cap, producing 500s and a React SSR error). PR #60 then found two problems with that first pass — it had only patched `docker-compose.prod.yml` while production actually runs `docker-compose.traefik.yml` (see [compose-file-topology-and-drift.md](compose-file-topology-and-drift.md)), and the *combination* of an absolute `max_server_memory_usage` cap with `max_server_memory_usage_to_ram_ratio: 0` was resetting the effective limit back to 0 — **ClickHouse treats `ratio: 0` as "0% of RAM", not "disabled"**, so the absolute cap got silently overridden to unlimited. The fix replaced the pair with the ratio-only setting at `0.85` (roughly 2.55 GiB on the 3 GiB container), per-query and spill thresholds unchanged. Never reintroduce an explicit `max_server_memory_usage_to_ram_ratio: 0` expecting it to mean "no ratio limit, use the absolute cap instead" — it means the opposite.

## init.sql — only runs on an empty datadir

`init.sql` is mounted read-only at `/docker-entrypoint-initdb.d/init.sql` in every compose file (dev and both prod variants). This path is ClickHouse's own convention: scripts under `docker-entrypoint-initdb.d/` run **only on first container start against an empty ClickHouse data directory** — not on every restart, and not idempotently against existing data. `DEPLOYMENT.md` says in step 4 that the schema is initialized "on the first start only" and has a "ClickHouse schema changes" section under Updating that tells the operator to apply a change by hand with `ALTER TABLE`; [../architecture.md](../architecture.md)'s "Storage" section states the run-once behaviour together with the logs TTL (next section). It is standard behaviour of the upstream image's entrypoint, not something telerithm's own code enforces, so a schema change to `init.sql` will not reach an already-initialized volume: that needs a manual `ALTER`/migration against the running container, whereas Postgres schema changes ship as Prisma migrations that the backend container applies at every start (`DEPLOYMENT.md`, "Database migrations").

## The logs table TTL: one fixed window, per-source retention not enforced

`init.sql` creates the `logs` table partitioned by day with a table TTL (`backend/clickhouse/init.sql:12-15#"TTL toDateTime(timestamp) + INTERVAL 30 DAY;"`): every log row expires 30 days after its `timestamp`, for every team and every source. That TTL is the only retention the log data has; no code in `backend/src` deletes log rows. ClickHouse applies a TTL when it merges parts, so an expired row can stay readable for a while after the 30 days pass.

Each `LogSource` in Postgres also carries a `retentionDays` column (`backend/prisma/schema.prisma:75#"retentionDays Int"`, default 7). `TeamService.createSource` always writes 7 (`backend/src/services/team/team-service.ts:201#"retentionDays: 7, apiKey"`), no route changes it (`PUT /sources/:id` changes the name and `POST /sources/:id/rotate-key` the ingest key), and the value is only returned with the source (`backend/src/services/team/team-service.ts:58#"retentionDays: s.retentionDays,"`). Nothing reads it to expire rows, so a source that reports 7 days keeps its logs for the 30 days of the table TTL. Deleting a source (`DELETE /sources/:id`) removes only its Postgres row and stops its ingest key from authenticating; the logs already stored for it are not deleted and stay until the same 30-day TTL expires them, because no code in `backend/src` issues a delete against the `logs` table.

To change the window on a running instance, editing `init.sql` is not enough, because it does not run again against an initialized volume (previous section). The table TTL changes with `ALTER TABLE logs MODIFY TTL toDateTime(timestamp) + INTERVAL <n> DAY`, the command `docs/architecture.md`'s "Storage" section gives; keep `init.sql` on the same value so a fresh volume matches. For a one-off cleanup of a shorter window, `DEPLOYMENT.md`'s "Maintenance" section runs `ALTER TABLE logs DELETE WHERE timestamp < now() - INTERVAL <n> DAY` instead.

## The anomalies table — provisioned, not wired

`init.sql` also creates an `anomalies` table (`team_id`, `detected_at`, `anomaly_type`, `severity`, `description`, `affected_services`, `sample_logs`, `resolved`) via `ENGINE = MergeTree() ORDER BY (team_id, detected_at)`. Grepping the backend and frontend source for `anomal` finds **zero references outside this schema definition** — no repository, service, or route reads or writes it. `README.md`'s feature list still carries "anomaly detection" under **Planned**, not shipped. This table is provisioned infrastructure for a not-yet-built feature, not dead code to clean up and not a bug to fix reactively — flagging it here as an explicit fact for an operator decision (build the feature, or drop the table) rather than editorializing which way that should go.

## Verify a config.d mount actually took effect — do not assume it

`CHANGELOG.md`'s `[0.1.1]` operational note already establishes the discipline for one of these files: "Verify `docker-compose.traefik.yml` is what is in effect on the host before assuming the new limits are applied: `docker exec <ch-container> cat /etc/clickhouse-server/config.d/limits.xml`." The same check applies identically to `system-logs.xml`. A stricter version, `ls -la` rather than `cat`, additionally catches a failure mode `cat` alone can miss: a broken or misconfigured host bind-mount can silently turn what should be a mounted config *file* into an empty *directory* instead — the container then boots with the override silently absent, no error, nothing to `cat`. This is the same class of host-side bind-mount contract fragility that surfaced in an unrelated 2026-07-15 incident on the same VPS-01 host. When in doubt after a deploy:

```bash
docker exec <clickhouse-container> ls -la /etc/clickhouse-server/config.d/
```

Expect `limits.xml`, `system-logs.xml` and `docker_related_config.xml` as regular FILES in `config.d/` (`init.sql` is mounted elsewhere, at `docker-entrypoint-initdb.d/`); a missing entry means the mount did not take effect and the container is running without that override.

The `users.d` mount needs the same check, and a stronger one, because a missing mount does not look broken: ClickHouse starts without the profile and every query runs uncapped. `docker exec <clickhouse-container> ls -la /etc/clickhouse-server/users.d/` lists `limits.xml`, and the settings themselves are the proof: `docker exec <clickhouse-container> clickhouse-client --query "SELECT name, value FROM system.settings WHERE name IN ('max_memory_usage', 'max_bytes_before_external_group_by', 'max_bytes_before_external_sort')"` returns 2147483648, 1073741824 and 1073741824; 0 means the profile is not applied.

**Why the compose files mount the directory and not the two files.** A bind mount of a single file pins that file's inode. A deploy runs `git pull`, and git writes a changed file as a new file, so the running container kept the old inode: with a Linux Docker host the container went on reading the old content until it was recreated, and `docker compose up -d` does not recreate it because the compose file did not change. Reproduced on a Linux Docker engine (colima, ext4): after a git-style replace of `limits.xml` and `docker compose up -d`, the container still held the old `limits.xml` with the single-file mounts, and holds the new one with the directory mount (same container id, no restart). A directory mount follows the host directory, so replaced files are seen at once. ClickHouse itself re-reads `config.d` periodically and applied a changed `max_server_memory_usage_to_ram_ratio` within seconds (checked with `system.server_settings`); changes to the system log tables (`system-logs.xml`) are read at server start, so they still need a ClickHouse restart (`docker compose restart clickhouse`). The first deploy after the switch recreates the container once because the mounts changed.

**What a directory mount hides.** The mount replaces the image's whole `config.d`, which holds `docker_related_config.xml` (`listen_host`, so the server accepts connections from other containers). `backend/clickhouse/config.d/docker_related_config.xml` is a copy of it (checked against the `clickhouse/clickhouse-server:24` image at 24.10.2.80). Without it the server listens on localhost only: the container's own health check (`clickhouse-client`) still passes while the backend cannot connect. Compare the copy with the image's file when the image tag moves. A malformed XML file in this directory (a `--` inside an XML comment is enough) makes ClickHouse exit at start and the container restart in a loop; a running server keeps its old config, so the error only shows at the next restart.

**The `users.d` mount and the image entrypoint.** The mount is read-only, like the `config.d` one. The image's `/entrypoint.sh` can write `users.d/default-user.xml`, and what triggers the write depends on the image. In 24.10.2.80 (the current `:24`) it writes the file (removes the `default` user, creates the one named by the variables) whenever `CLICKHOUSE_USER` is not `default`, or `CLICKHOUSE_PASSWORD` (also read from `CLICKHOUSE_PASSWORD_FILE`) or `CLICKHOUSE_DEFAULT_ACCESS_MANAGEMENT` is set. In 24.12.6.70 it writes a file on every start unless `CLICKHOUSE_SKIP_USER_SETUP=1` is set: with none of the variables set, a file that restricts `default` to localhost. Measured with the compose service: 24.10.2.80 with `CLICKHOUSE_USER=tele CLICKHOUSE_PASSWORD=secret`, and with `CLICKHOUSE_PASSWORD` plus the skip variable (24.10 ignores the skip variable), and 24.12.6.70 with no variable at all, each fail the write with "Read-only file system" and the container exits with status 1 at start, loudly and before any query. Without any `users.d` mount, 24.12.6.70 starts, but `default` accepts localhost only and a connection from a second container is refused (native: `AUTHENTICATION_FAILED`; HTTP on 8123: 403 with exception code 516), the way the backend, which connects over HTTP from its own container, would be refused. With `CLICKHOUSE_SKIP_USER_SETUP=1`, which both composes set, both versions start on the read-only mount, the three settings read 2147483648, 1073741824 and 1073741824, a cap-exceeding query fails with `MEMORY_LIMIT_EXCEEDED`, and `default` answers HTTP and native connections from a second container (measured from `docker-compose.prod.yml` and `docker-compose.traefik.yml` on both versions). On 24.12.6.70 the skip variable also makes the entrypoint ignore `CLICKHOUSE_USER` and `CLICKHOUSE_PASSWORD` without an error (measured with `CLICKHOUSE_PASSWORD`: the container starts and the log says "explicitly skip changing user 'default'"), so the compose files set none of the four variables. Mounting the directory read-write instead would let the entrypoint work (the profile applies to the new user) but writes `default-user.xml`, with the password in clear text, into the git checkout, so the mount stays read-only.

A user is defined with a file in `backend/clickhouse/users.d/` instead. Every file there and in `config.d` needs the `<clickhouse>` root element: a user file without it makes the server exit with status 232 (measured on 24.10.2.80). `<default remove="remove"/>` is a trap, because the compose health check (`clickhouse-client` as `default`) and `init.sql` on an empty data directory both connect as `default`: measured on 24.10.2.80 and 24.12.6.70, a fresh volume with `default` removed exits at the init step with `AUTHENTICATION_FAILED`, and on an initialised volume the health check query fails the same way. The recipe in `DEPLOYMENT.md` restricts `default` to `127.0.0.1` and `::1` (`<networks replace="replace">`) and adds the new user; measured with the snippet copied from that file, on both versions and on a fresh and an initialised volume: the container is healthy, `init.sql` creates its tables, the new user authenticates from a second container with the `default` profile applied (`max_memory_usage` 2147483648), and `default` is refused from there but works inside the container. `users.d` is reloaded within seconds, so the order matters: add the new user first, then point the backend's `CLICKHOUSE_URL` (written into the compose file) at it and recreate the backend, and only then restrict `default`; restricting `default` first cuts the backend off at once (measured on 24.10.2.80 and 24.12.6.70).

**What checks this in CI.** `scripts/clickhouse-config-guard.sh` (job "ClickHouse config") renders both prod composes and fails when the `clickhouse` service lacks the `init.sql`, `config.d` or `users.d` mount or mounts one read-write, when the two composes mount different sets, when an XML file under `config.d` or `users.d` is malformed or lacks the `<clickhouse>` root, when `config.d` holds a `<profiles>` block, when the service sets one of the four user variables, or when `CLICKHOUSE_SKIP_USER_SETUP=1` is missing. It also compares the two composes' rendered `logging` blocks and per-service limits and requires a bounded log, limits and a healthcheck on every service (see [compose-file-topology-and-drift.md](compose-file-topology-and-drift.md)). `scripts/clickhouse-config-guard.test.sh` applies each of these as a mutation to a copy and requires the guard to fail with the message of that branch. The guard checks the files, not the image: a new image tag still needs the manual check in `DEPLOYMENT.md` (start the tag once with both directories mounted read-only).
