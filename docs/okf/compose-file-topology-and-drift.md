## The invariant

Three compose files exist at the repo root and serve three different purposes, not three redundant copies:

- **`docker-compose.yml`** — local dev only. Sets `name: telerithm-dev` (a different project from the deployed stack's `telerithm`, so `docker compose up` on a host that also runs production cannot replace its containers) and publishes Postgres/ClickHouse/Redis ports on the loopback interface only (`127.0.0.1`: `5432`, `8123`/`9000`, `6379`). It has no per-service memory/CPU limits, no `x-logging` bound, and mounts only `backend/clickhouse/init.sql` into ClickHouse — no `limits.xml` (neither the `config.d` one nor the `users.d` profile), no `system-logs.xml`. Its backend carries a health check, the same `/api/v1/health` probe as `prod.yml` with shorter intervals, because `deploy/docker-compose.logging.yml` makes its Vector sidecar wait for `service_healthy`.
- **`docker-compose.prod.yml`** — a generic/reference production compose (internal-only Postgres/ClickHouse/Redis, `deploy.resources.limits` on every service, an `x-logging` anchor bounding json-file logs to `10m x 3`, the three ClickHouse mounts (`backend/clickhouse/init.sql`, the `backend/clickhouse/config.d` directory holding `limits.xml` and `system-logs.xml`, and the `backend/clickhouse/users.d` directory holding the settings profile in `limits.xml`)). It is **not** what is actually deployed anywhere; it exists as the non-Traefik reference shape (DEPLOYMENT.md). It sets `name: telerithm-standalone`, so its containers, network and volumes (`telerithm-standalone_pgdata`, `_chdata`, `_redisdata`) are disjoint from the deployed project's even when both are started from the production checkout.
- **`docker-compose.traefik.yml`** — the file **actually deployed** on VPS-01. Structurally the same service set and resource limits as `prod.yml`, plus an explicit `name: telerithm` (the project name the documented checkout directory `telerithm` always gave it, so the `telerithm_pgdata`/`telerithm_chdata`/`telerithm_redisdata` volumes and the `telerithm_telerithm-internal` network keep their names; a `COMPOSE_PROJECT_NAME` in the environment or in the `--env-file` would still override it), plus Traefik network wiring and routing labels (`traefik.http.routers.*`, `Host(...)` rules for `demo.telerithm.cloud`; `play.telerithm.cloud` appears only as an allowed CORS origin, not as a Traefik Host rule). `.relay.yml` (repo root) pins this explicitly: `compose_file: docker-compose.traefik.yml`, and its `post_update` hook (`docker compose -f docker-compose.traefik.yml exec backend npx prisma db push --skip-generate`) runs only against this file; there is no `pre_update` hook (it held only a pre-pull `build --no-cache`, dropped because agent-relay runs `pre_update` against the pre-pull tree and builds the pulled commit itself after the pull — `scripts/relay-config.test.sh` keeps it out). `DEPLOYMENT.md`'s entire deploy walkthrough also only ever invokes `-f docker-compose.traefik.yml`.

One deliberate asymmetry: `traefik.yml` sets `TRUST_PROXY: ${TRUST_PROXY:-1}` on the backend (Traefik is the single proxy hop, so the IP-keyed rate limiters key on the real client address, see `docs/configuration.md`), while `prod.yml` does not set it and so trusts no proxy. That is not drift: `prod.yml` has no proxy in front of the backend, and `TRUST_PROXY` is outside the operational-behaviour fields the next paragraph requires to stay identical. The same holds for the LLM settings: only `traefik.yml` wires `OPENAI_API_KEY`, the Groq `OPENAI_BASE_URL` and `OPENAI_MODEL` (default `openai/gpt-oss-120b`) into the backend; `prod.yml` sets none of them, so NLQ there runs on the heuristic fallback unless they are added.

Because `prod.yml` and `traefik.yml` are two independently-edited files describing what should be the same production runtime configuration, **the parts of them that encode operational behaviour, not routing, must be kept identical**: the three ClickHouse volume mounts (`init.sql` into `docker-entrypoint-initdb.d`, the `backend/clickhouse/config.d` directory over `config.d`, and the `backend/clickhouse/users.d` directory over `users.d`) the `clickhouse` service environment (`CLICKHOUSE_SKIP_USER_SETUP: "1"`, see [clickhouse-retention-and-memory-limits.md](clickhouse-retention-and-memory-limits.md)), and the `x-logging: &default-logging` anchor (`json-file`, `max-size: "10m"`, `max-file: "3"`) applied to every service. Neither file sets a `NODE_OPTIONS` heap flag on the backend: Node 22 already caps its default heap at about half of the container limit (roughly 259 MB at 512M), and an explicit `--max-old-space-size=384` was measured to raise the heap above that default and turn a JavaScript heap error (exit 133) into an OOM kill (exit 137), so the mirrored fields do not include a heap flag. `docker-compose.yml` (dev) is deliberately exempt from this — it never runs against production data volumes and intentionally omits both.

## Where it's enforced

`prod.yml` carries its own `name: telerithm-standalone`; before that it had none, so its project name was the directory basename and on the VPS checkout (`telerithm`) it resolved to the deployed project and the same volumes, and `docker compose -f docker-compose.prod.yml up` would recreate the production containers without the Traefik labels (and without `OPENAI_*` and `TRUST_PROXY`). `traefik.yml` keeps `name: telerithm`: the live volumes and network derive from it, so changing it would orphan the production data. The ClickHouse part of the invariant and the naming are checked in CI: `scripts/clickhouse-config-guard.sh` renders both composes and fails when `prod.yml` has no top-level `name:`, when the two share a project name, a volume or a network (except the external `traefik` network), when `traefik.yml`'s project is not `telerithm` or its volumes are not `telerithm_pgdata`, `telerithm_chdata`, `telerithm_redisdata`, and fails when the `init.sql`, `config.d` and `users.d` mounts differ between them, are missing or are not read-only, or when the `clickhouse` service environment sets one of the user variables or lacks `CLICKHOUSE_SKIP_USER_SETUP=1` (the `x-logging` anchor is not part of that check). The rest (the logging anchor, the resource limits) is a hand-maintained invariant, not a structural one (unlike the by-id-write-route guard in [api-authz-and-team-scoping.md](api-authz-and-team-scoping.md), which has an AST meta-test). For the rest the only enforcement is discipline at edit time and the operational-note habit `CHANGELOG.md` documents: verify the mount that matters is actually present in the file that is actually deployed (see [clickhouse-retention-and-memory-limits.md](clickhouse-retention-and-memory-limits.md), "Verify a config.d mount actually took effect").

## What breaks it — the drift precedent

Three commits show the exact failure mode and its eventual fix:

- **PR #59** (`CHANGELOG.md [0.1.1]`) raised the ClickHouse container to 3 GiB and introduced `limits.xml` after an OOM — but only patched `docker-compose.prod.yml`.
- **PR #60** had to catch up: "PR #59 only patched `docker-compose.prod.yml`, but production runs via `docker-compose.traefik.yml`. The limits mount and 3 GiB cap are now mirrored into the traefik compose, so the fix lands on the deployed container." This is the drift risk made concrete — a real fix shipped and did not reach production until a dedicated follow-up commit noticed the gap.
- **PR #110** (commit `b3744ec`/`7248959`) is the corrected pattern: it introduced `system-logs.xml`'s mount and the `x-logging` bounding "in both prod composes" and "on all services in both prod composes" in the same commit, per its own message — no separate mirroring PR was needed this time.

Any future change to ClickHouse's `config.d`/`users.d`/`docker-entrypoint-initdb.d` mounts, resource limits, or the logging anchor must land in both `docker-compose.prod.yml` and `docker-compose.traefik.yml` in the same change (PR #110's pattern), not just the one a developer happens to be looking at (PR #59's pattern) — otherwise the fix silently does not reach the deployed container, exactly as PR #60 had to discover and correct after the fact.
